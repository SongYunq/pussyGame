## 二、 已实现的发牌构建规则

### 2.1 牌库与参与者

| 规则编号 | 规则 |
| :--- | :--- |
| DEAL-001 | 使用一副标准 52 张扑克，不含大小王。花色为 `spades`、`hearts`、`clubs`、`diamonds`；点数为 2～14，其中 11/12/13/14 对应 J/Q/K/A。 |
| DEAL-002 | 以“花色 + 点数”唯一标识一张实体牌；同一局所有玩家的手牌不得重复。 |
| DEAL-003 | 正常联机流程在至少 2 名在座玩家且全员准备后自动开局；房间最多 8 个座位。 |
| DEAL-004 | 服务端先逐人扣除底注，再为状态为 `active` 的玩家发牌；底注扣除失败的玩家改为 `sitting` 并取消准备，不进入本次发牌集合。 |
| DEAL-005 | 每名参与玩家恰好获得 3 张牌，采用同一副牌无放回分配。8 人局共用 24 张，剩余 28 张不参与本局手牌。 |
| DEAL-006 | 每局重新创建并洗乱完整牌库，不沿用上一局剩余牌；当前没有玩家换牌、补牌或按胜负重发的机制。 |

### 2.2 洗牌步骤与随机来源

当前前后端均采用 Fisher-Yates 洗牌，步骤如下：

1. 生成完整的 52 张牌数组。
2. 从末尾下标 `i = 51` 向前遍历到 `i = 1`。
3. 计算 `j = Math.floor(Math.random() * (i + 1))`，从下标 0～i 中选择交换位置。
4. 交换下标 i、j 的牌，直到遍历结束。

服务端 `Deck.shuffle(cards)` 先复制输入数组，不改变原数组；前端直接打乱本次新建的牌库。洗牌时间复杂度为 O(N)。

在每次随机选择均匀且独立的假设下，该算法使各牌序等概率。当前随机来源是 `Math.random()`，没有可指定种子或回放随机序列的机制，也没有使用密码学安全随机源；不应将当前实现描述为可审计的“真随机”。

### 2.3 发牌顺序与双端差异

* **联机服务端**：按座位数组顺序遍历有效玩家，每人连续从牌库末尾 `pop()` 取 3 张。
* **前端独立模拟**：按座位数组顺序遍历所有有用户的座位，每人连续从牌库开头读取 3 张；不执行服务端的全员准备和数据库底注校验。
* 当前两端均为“每人一次分配 3 张”，没有按庄家起点逐轮每人发 1 张。庄家影响联机首位行动玩家，不改变本局分牌顺序。
* 两端独立洗牌，取牌方向也不同，不保证生成同样的具体牌面；共同约束是牌库合法、每人 3 张、全桌无重复。
* 当前实际发牌不按账号、筹码、历史输赢、新老玩家身份或管理员权重挑选手牌。

### 2.4 手牌可见性

* 联机完整手牌由服务端持有；`game:start` 向参与者分别发送本人手牌。
* `Room.getMaskedState(forUserId)` 只保留本人 `cards`，其他玩家以及观战视角中的手牌为 `null`。
* `hasLooked` 控制是否已看牌及相关交互；当前本人手牌在开局时已发送到本人客户端，并非点击看牌后才首次下发。
* 前端独立模拟在 `secretCards` 中保存全桌手牌，对外状态只暴露本人手牌。此机制用于本地演示，联机发牌结果和裁判以服务端为准。

## 三、 牌型规则与自然概率基线

### 3.1 牌型识别约定

发牌负责生成合法手牌，牌型识别负责对手牌分类。服务端裁判见 [GameReferee.ts](../server/src/game/GameReferee.ts)，前端展示与独立模拟裁判见 [pokerEvaluator.ts](../client/src/utils/pokerEvaluator.ts)。

| 牌型 | 类型标识 | 当前判定与比较规则 |
| :--- | :--- | :--- |
| 豹子 | `leopard` | 三张点数相同；正常等级最高 |
| 顺金 / 同花顺 | `straight_flush` | 同花且连续 |
| 金花 / 同花 | `flush` | 同花且不连续 |
| 顺子 | `straight` | 非同花且连续 |
| 对子 | `pair` | 恰好两张点数相同；先比较对子，再比较单牌 |
| 散牌 | `high_card` | 不属于上述牌型，按点数从大到小比较 |
| 特殊 235 | `special_235` | 点数恰为 2、3、5 且非同花；仅在与豹子直接比较时逆袭，其余按最小散牌处理 |

* 普通牌型等级为：豹子 > 顺金 > 金花 > 顺子 > 对子 > 散牌。
* A-2-3 是最小顺子或顺金，Q-K-A 是最大顺子或顺金；不接受 K-A-2。
* “非同花 235”表示三张牌不全同花，不要求三张花色各不相同；同花 235 属于金花。
* 花色不用于大小比较；牌型、比较点数相同时，主动发起比牌的一方判负。
* 特殊 235 与豹子的关系是两手牌之间的特殊规则，不能简单给 235 设置一个全局最高分。当前服务端多人摊牌按传入顺序逐个比较，后加入比较的玩家为挑战者；混合出现豹子、235 和其他牌型时，结果可能受顺序影响。修改此规则时须单独记录多人裁决方案。

### 3.2 自然发牌概率

从完整 52 张牌中任取 3 张，共有 `C(52, 3) = 22,100` 种无序组合。按当前裁判支持 A-2-3 与 Q-K-A 的规则，单名玩家的手牌分布为：

| 统计分类 | 组合数 | 理论概率 |
| :--- | ---: | ---: |
| 豹子 | 52 | 0.235294% |
| 顺金 | 48 | 0.217195% |
| 金花，不含顺金 | 1,096 | 4.959276% |
| 顺子，不含顺金 | 720 | 3.257919% |
| 对子 | 3,744 | 16.941176% |
| 散牌，含特殊 235 | 16,440 | 74.389140% |
| 合计 | 22,100 | 100% |

特殊 235 共 60 种，约占 0.271493%，已计入上表散牌；若单列特殊 235，普通散牌为 16,380 种，不可重复计数。

这些比例是单手牌的理论分布，不是整桌出大牌概率或玩家胜率。多人同桌共享一副牌，各手牌并不独立；有限样本的实际次数允许波动，不要求精确等于期望次数。

## 四、 管理端调控设计与待实现范围

### 4.1 已有模式与参数

界面已有 `fair`、`action_boost`、`beginner_favor`、`custom` 四种模式，分别对应自然平衡、激烈碰撞、新手偏好和自定义。当前这些值只影响管理端配置及估算显示，不改变联机或前端独立模拟中的真实发牌。

下表记录前端 `AlgorithmConfig` 与现有接口文档约定，作为后续接入时的核对清单；范围尚未由服务端校验：

| 字段 | 默认值 | 约定范围 | 当前用途与实现边界 |
| :--- | :--- | :--- | :--- |
| `mode` | `fair` | 上述四种模式 | 模式选择和界面预设 |
| `leopardWeight` | 1.0 | 0.1～5.0 | 豹子概率估算系数 |
| `straightFlushWeight` | 1.0 | 0.1～5.0 | 顺金概率估算系数 |
| `flushWeight` | 1.0 | 0.1～4.0 | 金花概率估算系数 |
| `straightWeight` | 1.0 | 0.1～3.0 | 顺子概率估算系数 |
| `pairWeight` | 1.0 | 0.1～2.0 | 对子概率估算系数 |
| `highCardWeight` | 1.0 | 0.1～2.0 | 散牌概率估算系数 |
| `clashRate` | 25 | 0～100 | 尚无实际强强碰撞生成或统计逻辑 |
| `special235Boost` | 1.0 | 0.1～5.0 | 尚无实际特殊 235 生成加权逻辑 |
| `playerLuckWeights` | `{}` | 用户编号对应 -50～+50 | 尚无个人手牌倾斜逻辑 |

默认 `fair` 配置中虽然包含 `clashRate: 25`，但不能据此推导“自然发牌有 25% 强强碰撞率”；该字段当前未参与发牌，也未参与管理端估算。

### 4.2 当前估算与真实仿真的区别

管理端当前使用以下计算过程：

```text
某类估算概率 = 该类基础概率 × 该类权重 / 所有类别加权概率之和
某类估算次数 = round(样本数 × 某类估算概率)
散牌次数 = 样本数 - 其他五类估算次数之和
```

基础概率使用代码中的四舍五入常量；计算只涉及六类牌型权重，不使用 `clashRate`、`special235Boost` 或 `playerLuckWeights`。当前过程没有随机采样，也未处理整桌共用牌库的约束，因此结果只能作为概率估算，不能证明实际发牌效果。

配置随界面状态保存到浏览器本地；点击保存还会尝试请求服务端，但当前错误被捕获后仍提示成功。现有界面中的“立即生效”“真实发牌仿真”“已接通本地引擎”等描述不代表这些能力已实现。

### 4.3 后续构建前需要明确的规则

以下事项仍为待确定或待实现，不能视为本次已决定的算法方案：

1. **权重含义**：明确相对概率、目标牌型占比与实际生成方法之间的关系；同桌多手牌必须满足实体牌不重复的约束，并定义无法满足目标时的处理方式。
2. **模式定义**：记录各预设的完整参数及选用逻辑；新手偏好需明确新手资格、偏好幅度和结束条件。
3. **强强碰撞与特殊 235**：定义“大牌”和碰撞事件的统计口径、人数影响，以及参数如何影响牌型和整桌分布。
4. **个人参数**：明确生效对象、有效期限、多个玩家同时设置时的处理方式及可验证的效果指标。
5. **配置生效**：明确全局或房间作用域、持久化位置、版本、失败处理和回退方式，以及是否只影响下一局；不得把浏览器本地保存等同于服务端生效。
6. **真实仿真**：调用与正式对局相同的发牌实现，明确按局还是按手统计、参与人数、样本规模、参数和算法版本；需要复现时再设计可控随机来源。
7. **异常边界**：补齐底注扣除失败后有效玩家不足 2 人等场景的处理与验证；当前 `Room.startGame()` 在扣注后没有重新检查最低有效人数。
